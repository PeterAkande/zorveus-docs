[Install the CLI](/cli/installation), then run these commands from your project directory.

---

## Option 1: Interactive wizard (`zorveus setup`)

For a guided setup that configures your app, allowed models, customer allowance plans, optional routing key, and a read-only customer service key in one pass, run:

```sh
zorveus setup
```

For a local Zorveus backend, run `zorveus setup --local`.

The wizard handles sign-in if needed, asks for your app name, allowed models (`*` by default), credit units per USD (`100` by default), one or more monthly plans (such as `plus` at `$10/month`), and whether to add a routing key. It then writes `zorveus.json` (including `organizationId`), previews the plan, and creates the resources after you confirm.

Run `zorveus setup` again anytime to review or edit an existing `zorveus.json` while keeping your resource IDs intact.

## Option 2: Manual manifest workflow

If you prefer editing JSON directly, follow the four-step `init` → `validate` → `plan` → `apply` workflow.

### 1. Sign in

```sh
zorveus login
zorveus whoami
```

Choose the organization that owns the app. Confirm `whoami` shows the right organization. (Use `zorveus login --local` for a local backend.)

### 2. Create and validate a manifest

```sh
zorveus init --name "Assistant"
```

`init` creates `zorveus.json` with `allowedModels: ["*"]` and refuses to overwrite an existing file. Pass `--starter saas` to generate a SaaS plan starter, or copy one of the [example manifests](/cli/examples).

Edit `zorveus.json` to add an API key with a monthly `$100` cap and a routing key:

```json
{
  "version": 1,
  "app": {
    "name": "Assistant",
    "allowedModels": ["*"]
  },
  "keys": {
    "backend": {
      "name": "Backend",
      "cap": {
        "amount": "100",
        "currency": "USD",
        "period": "monthly"
      }
    }
  },
  "routingKeys": {
    "primary": {
      "name": "Assistant router",
      "members": ["backend"],
      "defaultSelector": "backend"
    }
  }
}
```

Validate the JSON offline:

```sh
zorveus validate
```

### 3. Review and apply changes

<span id="review-and-apply-changes" />

```sh
zorveus plan --config zorveus.json
```

`plan` saves `zorveus.plan.json` without changing remote resources, showing `+` for additions, `~` for updates (`old -> new`), and `-` for removals. Pass `--no-color` or set `NO_COLOR=1` to disable ANSI colors.

Apply the saved plan and confirm everything is in sync:

```sh
zorveus apply --plan zorveus.plan.json --yes
zorveus status --config zorveus.json
```

`apply` creates or updates the resources, writes `organizationId` and the created resource IDs back into `zorveus.json`, and saves generated secrets into your OS credential store. Secrets never appear in manifests, saved plans, or apply output.

## Retrieve saved secrets

Use `zorveus retrieve` to print a saved secret from your OS credential store by its manifest reference or backend ID:

```sh
zorveus retrieve keys.backend
zorveus retrieve routingKeys.primary
zorveus retrieve serviceKeys.customers
zorveus retrieve app
```

| Reference | Secret returned |
| :--- | :--- |
| `app` | OAuth client secret (confidential apps only). |
| `keys.<name>` | API key (`zrv_...`). |
| `routingKeys.<name>` | Routing key (`zrv_route_...`). |
| `serviceKeys.<name>` | Service key (`zrv_svc_...`). |

Pass `--config zorveus.dev.json` for non-default manifests, or pipe directly to your clipboard on macOS (`zorveus retrieve keys.backend | pbcopy`). Use `--json` in scripts to receive `{ item, id, secret }` in the standard envelope. `retrieve` never rotates a key and is not exposed through MCP.

## Make an update and check drift

Edit `app.name` in `zorveus.json` (keeping all resource IDs intact), then check drift, plan, and apply:

```sh
zorveus status --config zorveus.json --json
zorveus plan --config zorveus.json --out rename.plan.json
zorveus apply --plan rename.plan.json --yes
zorveus status --config zorveus.json --json
```

Before apply, `status` reports `result.in_sync: false` with the name diff. After apply, `result.in_sync` returns `true` with the same resource IDs.

### Removing resources

- Omitting an optional field or whole section preserves existing values.
- Removing a managed key or router from an explicit `keys` or `routingKeys` object proposes revoking it.
- Plans with revocations, cap removals, or redirect removals require `--allow-delete`:

```sh
zorveus apply --plan removal.plan.json --yes --allow-delete
```

Removing `serviceKeys` or `providerCredentials` entries from a manifest leaves those shared organization resources active. To tear down an entire app and all listed credentials at once, use [`zorveus destroy`](/cli/state-and-destroy#destroy-a-deployment).

### Resume an interrupted apply

Keep the saved plan and `.zorveus/` directory beside your manifest, then run the same apply command again:

```sh
zorveus apply --plan zorveus.plan.json --yes
```

With S3-compatible durable state, another machine can resume without the local plan file using `zorveus apply --resume --config zorveus.json --yes`.

## Adopt an existing app

If your app already exists in the dashboard, import it into a new manifest instead of creating a duplicate:

```sh
zorveus import --app-id app_example --config imported.json
zorveus status --config imported.json
zorveus plan --config imported.json
```

`import` records `organizationId`, app settings, active programmatic API keys, and routing keys while leaving secrets, end-user OAuth connections, service keys, and BYOK credentials out. Both the destination manifest and its local state must be new.
