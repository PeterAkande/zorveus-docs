title: Rate limits and retries
description: Handle 429 throttling safely, understand which endpoints are safe to retry, and use external_reference for idempotent credit grants.
---

Zorveus does not use a universal `Idempotency-Key` header. Instead, retry safety depends on the operation you are calling, and credit grants use `external_reference` to prevent duplicates.

---

## Rate limits (`429`)

Rate limits vary by route, deployment, and the upstream provider or BYOK account serving your request. When throttled, Zorveus returns HTTP `429 Too Many Requests`.

For retryable requests:

1. Honor the `Retry-After` header when present.
2. Use exponential backoff with random jitter.
3. Cap total retry attempts and set an overall timeout.
4. Reduce request concurrency if throttling continues.

Do not retry authentication failures (`401`), wallet shortfalls (`402`), or exhausted caps and allowances (`403`) until the underlying issue is fixed.

---

## What is safe to retry

### Reads

Profile reads, allowance checks, credit-grant lists, model discovery, and key usage reads are safe to retry. Values can change between attempts.

### Customer profile upserts

`PUT /product-users/by-external-id` creates or updates the same customer for `(app_id, external_user_id)`. Repeating the same request does not create duplicate customers.

### Model requests (inference)

Model requests are **not** deduplicated. Retrying after a timeout or dropped stream can trigger a second provider call and a second charge. Bound retries and retry only when your app can tolerate a duplicate completion.

### OAuth token exchange and revocation

Authorization codes are single-use. If token exchange succeeds on Zorveus but your app loses the response, retrying the same code returns `zorveus_oauth_code_consumed`; start the connect flow again to get a new token. Repeating `POST /oauth/revoke` on an already-revoked token safely returns `{ "revoked": false }`.

## Idempotent credit grants (`external_reference`)

Always include `external_reference` when calling `POST /product-users/by-external-id/credit-grants`, such as `purchase:ch_123` or `welcome:customer_42`. Repeating the same `external_reference` with matching parameters returns the existing grant instead of crediting the customer twice, even under concurrent retries.

### Rules for `external_reference`

- Case-sensitive, trimmed of leading/trailing whitespace, 1 to 255 characters.
- Unique per organization and app across all credit grants (not scoped per service key, user, or source). Add a prefix such as `purchase:` or `welcome:` to separate grant types.
- **Parameter matching**: Replays must match on external user ID, numeric amount, currency, source, reason, expiry (compared in UTC), all metadata, and explicit `credit_units_per_usd` when provided. Missing metadata and `{}` count as different values. Display name and email are ignored on replay.
- **Mismatched replay (`409`)**: Reusing an `external_reference` with different parameters returns HTTP `409 Conflict` (`zorveus_product_user_credit_reference_conflict`). Never generate a fresh random reference to bypass a `409`; inspect the original grant first.
- **Permanent retention**: The reference stays attached even after a grant is spent, expired, or revoked. Replaying returns the grant's current state rather than restoring its balance.

### Recovering from a timeout or lost response

1. Repeat the original `POST /product-users/by-external-id/credit-grants` with the exact same `external_reference` and parameters, or look up the grant with `GET /product-users/by-external-id/credit-grants/by-reference` (`app_id`, `external_user_id`, `external_reference`).
2. A `404` on lookup does not prove an in-flight `POST` failed. Repeat the original `POST` with the same `external_reference` so Zorveus either returns the committed grant or creates it if the first attempt rolled back.

Calls without `external_reference` (or with `null`) create a new grant every time. The SDKs do not automatically retry credit-grant `POST` requests. See [Grant customer credits](/startups/credit-grants#grant-credits-after-a-payment).
