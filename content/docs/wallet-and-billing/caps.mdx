---
title: Spending caps
description: Set daily, monthly, or lifetime spending caps, understand how caps combine with credits, and configure overrun policies.
---

Spending caps limit how much AI usage an organization, app connection, or individual customer can consume in a period. A cap is a spending ceiling, not a prepaid deposit.

Configure and monitor caps in the [Zorveus dashboard](https://app.zorveus.com).

---

## Set a cap in the dashboard

1. Open the [Zorveus dashboard](https://app.zorveus.com) and go to **Apps**.
2. Select your app and open **Connection settings**.
3. Under **Spending caps**, set:
   - **Cap amount**: Maximum reference-priced spend allowed in each period (for example, `$50.00`).
   - **Period**: `daily`, `monthly`, or `lifetime`.
   - **Allowance overrun policy**: What happens if a model reply could cost more than the remaining allowance.
4. Save your changes. New requests follow the updated policy right away.

The dashboard shows a live progress bar for each cap with current period spend, remaining base allowance, and the next reset time.

---

## Cap levels

Zorveus enforces caps at three levels:

- **Organization cap**: Set under **Settings** → **Billing**. Caps total AI spend across every app and key in the organization.
- **App-connection cap**: Set on the app connection. When requests include a customer ID (`X-Zorveus-External-User-ID`), each customer gets their own separate allowance from this cap. Under `enforce`, requests without a customer ID share a separate connection-level total.
- **Product-user cap**: Sets an explicit limit for an individual customer within an app. Monitor per-customer spend under **Product Users** in the dashboard.

When more than one cap applies, every cap must have room for the request to go through. Lowering a cap affects future requests and never alters already-settled usage.

## How caps and customer credits combine

When an API key has a cap, a customer's spendable allowance is their remaining base cap plus any active credit grants:

```text
remaining allowance = remaining base allowance + available product-user credits
```

Where remaining base allowance is:

```text
remaining base allowance = max(0, cap amount - completed period spend - active reservations)
```

### Consumption order

Zorveus draws from a customer's allowance in this order:

1. **Remaining base allowance** from the cap.
2. **Available product-user credits** (soonest-expiring grants first).
3. **Uncovered spend** (only in `track_only` mode or when an overrun policy allows a call to finish past the cap).

Example:

```text
Configured monthly cap:        $10.00
Spend so far this period:       $8.00
Remaining base allowance:       $2.00
Available user credits:         $5.00

Incoming request estimate:      $3.00
Base allowance reserved:        $2.00
Credits reserved:               $1.00
Remaining credits after call:   $4.00
```

The base cap covers the first `$2.00`, and customer credits cover the remaining `$1.00`.

---

## Uncapped connections

When no cap is configured on a connection:

- Customer allowance is unlimited, so requests are not rejected for allowance limits.
- Usage is still logged in **Usage** analytics.
- Product-user credits are not consumed.

Customer credits extend a configured cap. They do not act as a limit on an uncapped connection.

---

## Overrun policies

In **Connection settings**, **Allowance overrun policy** controls what happens when a model reply might exceed the remaining allowance:

| Policy | Dashboard label | During the request | Excess spend |
| :--- | :--- | :--- | :--- |
| `limit_output` (default) | Limit output tokens | Lowers max output tokens to fit the remaining allowance. | Any small variance is logged as uncovered spend. |
| `allow_overrun` | Allow overrun | Sends the request's full output limit. | Excess is logged as uncovered spend and forgiven on the next reset. |
| `carry_overrun_forward` | Carry overrun forward | Sends the request's full output limit. | Excess is recorded as debt and repaid from the next credit grant or cap reset. |

If an enforced request already exceeds remaining allowance before dispatch, the gateway rejects it with HTTP `403 Forbidden` (`zorveus_product_user_allowance_insufficient` or `zorveus_cap_exceeded`). See [Error handling](/platform/errors) for the full payload.
