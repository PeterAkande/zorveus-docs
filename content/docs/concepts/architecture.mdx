title: How Zorveus works
description: Understand how your app, Zorveus, AI model providers, and customer allowances fit together.
---

Zorveus sits between your app and AI model providers. Your backend sends model requests to Zorveus, which checks access and spending limits, routes each call to the provider, and records usage against your organization and customer.

You configure apps, API keys, spending caps, and provider credentials in the [Zorveus dashboard](https://app.zorveus.com). Your app does not need to build its own provider routing or per-customer AI metering.

## The system at a glance

<ArchitectureDiagram />

Each surface uses its own credential:

| Surface | What you do | Credential |
| :--- | :--- | :--- |
| **Dashboard** | Configure apps, API keys, spending caps, BYOK provider keys, team roles, and webhooks. | Dashboard sign-in |
| **Inference gateway** | Send chat, image, audio, embedding, or other model requests to `https://api.zorveus.com/v1`. | API key (`zrv_...`), routing key (`zrv_route_...`), or user OAuth token (`zrv_usr_...`) |
| **Service API** | Read balances, update customer profiles, and grant credits under `/product-users/by-external-id`. | Server-only service key (`zrv_svc_...`) |

## Building blocks with one example

Suppose you are adding AI to a customer-support product where your company pays for model usage and gives each customer a monthly limit:

| Concept | What it is | Example |
| :--- | :--- | :--- |
| **Organization** | Workspace that owns funding, credentials, and team access. | Your Business organization |
| **App** | Identity for the product you are integrating. | Support Assistant |
| **API key** | Secret that authenticates model calls and carries allowed models, spending caps, and credit rules. | Your Pro plan key (`zrv_...`) |
| **Product user** | Your end customer, identified by your own user ID. | `customer_123` (not a Zorveus dashboard member) |
| **Provider key (BYOK)** | Optional upstream API key for OpenAI, Anthropic, Gemini, or another provider. | Your company OpenAI key in **Provider Credentials** |
| **Wallet** | Cash balance that pays for managed model calls and applicable BYOK platform fees. | Your Business wallet |
| **Cap and credits** | Rules that control how much AI a customer can use. | `$10/month` cap plus a `$5` credit grant |

## Follow one request end to end

Your customer `customer_123` asks the assistant a question:

1. Your backend selects the Zorveus API key (or routing key + plan alias) for that customer's plan.
2. Your backend sends the model request with `X-Zorveus-External-User-ID: customer_123` (or `metadata.external_user_id` in the body). Zorveus creates the customer record automatically on their first request.
3. Zorveus checks the API key's allowed models, the customer's remaining cap and credits, and available funding.
4. For wallet-funded requests, Zorveus holds an estimated charge from your wallet. For BYOK requests, Zorveus picks the highest-priority eligible provider key and holds any applicable platform fee.
5. The model provider runs the request and Zorveus returns the response (or streams tokens back).
6. Zorveus records actual token usage, settles the final charge, and releases any unused hold.

Streaming changes how output reaches your app, not how limits or billing work. If a stream disconnects early, Zorveus reconciles the hold once the upstream call settles.

To show a customer's balance in your UI before they send a request, use [Show a customer's balance](/startups/check-allowance). That read is a point-in-time snapshot; Zorveus still checks the live request before running the model. To react to events such as a customer reaching a cap or a top-up settling, configure [Webhooks](/platform/webhooks).
