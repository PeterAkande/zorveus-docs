---
title: Models and routing
description: Understand how model allowlists, routing keys, and BYOK provider key priority work together on every request.
---

Your request always names a concrete model ID (such as `openai/gpt-4.1-mini` or `anthropic/claude-sonnet-5`). Zorveus never swaps your model ID automatically. Instead, three separate layers decide whether the model is allowed, which plan rules apply, and which upstream key executes the call.

---

## 1. Allowed model policies

Every API key defines which models it can call using one of three formats:

- `*`: Any model available in the Zorveus catalog.
- `provider/*`: Any model whose ID starts with that provider and a slash (for example, `openai/*` or `anthropic/*`). Partial prefixes such as `anthropic/claude-*` are not wildcards.
- `provider/model-name`: One exact model ID.

Call `GET /v1/models` with your API key to list the concrete models allowed for that key. If you use a routing key, include `X-Zorveus-Key-Alias` to inspect a specific plan's models. The [public model catalog](/api-reference/models) shows capabilities across Zorveus, but it does not override your API key's allowed-model policy.

Allowing a model permits access through Zorveus; it does not create a custom deployment (such as on Azure OpenAI) or guarantee upstream provider capacity.

---

## 2. Plan selection with routing keys

A [routing key](/startups/routing-keys) (`zrv_route_...`) lets your backend use one secret across multiple subscription plans. Pass `X-Zorveus-Key-Alias` (or `metadata.key_alias` in the body), and Zorveus applies the matching plan key's allowed models and spending cap.

A routing key selects **policy**, not a different model. Your backend still chooses the `model` field in the request.

---

## 3. Upstream key priority and fallback (BYOK)

Once the model and plan rules pass, Zorveus chooses how to reach the upstream provider:

- If your organization has active [BYOK provider keys](/startups/provider-credentials) matching that model, Zorveus tries them in priority order (explicit grants first, then lowest `routing_priority` number).
- If a key hits an eligible upstream error or rate limit, Zorveus rotates to the next healthy backup key.
- If no BYOK key matches, or if `auto_fallback_to_wallet` is enabled after eligible BYOK failures, Zorveus routes through its managed wallet path.

See [Key priority, rotation, and fallback](/startups/automatic-routing) for the exact ordering and fallback rules.
