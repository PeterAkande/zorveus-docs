## Policy expansion

When your App Connection defines wildcard policies like `*` or `openai/*`, the `/v1/models` endpoint **expands those wildcards into concrete routable model IDs** (e.g. `openai/gpt-6-sol`, `openai/gpt-6-sol`, `anthropic/claude-sonnet-5`)

Wildcard strings are policy configurations. They are not valid target model identifiers in chat completion requests

## Code example

<CodeGroup titles={["Python (OpenAI SDK)", "TypeScript (OpenAI SDK)", "cURL"]}>

```python
from openai import OpenAI

client = OpenAI(
    base_url="https://api.zorveus.com/v1",
    api_key="zrv_your_api_key",
)

models = client.models.list()
for model in models.data:
    print(f"Available Model: {model.id} (Owner: {model.owned_by})")
```

```typescript
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: "https://api.zorveus.com/v1",
  apiKey: "zrv_your_api_key",
});

async function main() {
  const models = await client.models.list();
  for (const model of models.data) {
    console.log(`Available Model: ${model.id} (Owner: ${model.owned_by})`);
  }
}

main();
```

## Read the response

A successful response has `object: "list"` and a `data` array. Each item contains a concrete `id`, `object: "model"`, and ownership metadata. Use the returned `id` unchanged in inference requests

With a routing key, send `X-Zorveus-Key-Alias` to discover the chosen member's allowed models. If no alias is sent, a configured default member is required

Use the [public catalog](/api-reference/models) for task capabilities and pricing fields. A key-scoped list is an access check, not proof that every endpoint or optional parameter works with every listed model
