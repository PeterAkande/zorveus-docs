---
title: Product users and credits API
description: Read profiles, update users, and grant credits with a server-side service key.
---

All routes on this page use `https://api.zorveus.com` without `/v1`. Send `Authorization: Bearer zrv_svc_...` from your backend. The service key determines the organization. Supply `app_id` and your stable `external_user_id` to identify the customer

| Operation | Method and path | Scope |
| --- | --- | --- |
| Read profile and allowance | `GET /product-users/by-external-id` | `product_users:read` |
| Create or update profile | `PUT /product-users/by-external-id` | `product_users:write` |
| Read credit balance | `GET /product-users/by-external-id/credit-summary` | `product_users:read` |
| Read carried allowance debt | `GET /product-users/by-external-id/allowance-debt` | `product_users:read` |
| Grant credits | `POST /product-users/by-external-id/credit-grants` | `product_users:write` |
| List grants | `GET /product-users/by-external-id/credit-grants` | `product_users:read` |
| Find a grant by reference | `GET /product-users/by-external-id/credit-grants/by-reference` | `product_users:read` |
| List usage and credit activity | `GET /product-users/by-external-id/activity` | `product_users:read` |

`product_users:write` also permits these reads. Prefer the narrower scope for a read-only backend. Change user status and revoke grants in the dashboard

## Get product user by external ID

<ApiEndpoint method="GET" path="/product-users/by-external-id" auth="service_key" />

Required query fields are `app_id` and `external_user_id`. HTTP `200` returns the profile directly. By default, a read does not create a user. A missing user returns HTTP 404 with `zorveus_product_user_not_found`. The optional upsert header below enables creation

```bash
curl --fail-with-body --get https://api.zorveus.com/product-users/by-external-id \
	-H "Authorization: Bearer $ZORVEUS_SERVICE_KEY" \
	--data-urlencode "app_id=$ZORVEUS_APP_ID" \
	--data-urlencode 'external_user_id=customer_42'
```

| Response field | Meaning |
| --- | --- |
| `product_end_user_id`, `org_id`, `app_id`, `external_user_id` | Internal user ID, owning organization, app, and your customer ID |
| `display_name`, `email_hash`, `metadata`, `status` | Profile fields. The email is returned as a hash |
| `allowance_starts_at` | Stored subscription anchor, or null for calendar periods |
| `last_app_connection_id` | Last connection used to resolve the customer's policy |
| `usage.this_period`, `usage.total` | Usage buckets with `sell_cost`, token counts, and `request_count` |
| `usage.period_start`, `usage.period_end` | Current usage window |
| `cap`, `direct_cap` | Resolved cap and explicit user cap, when present |
| `credits` | Credit summary, independent of remaining base allowance |
| `allowance` | Effective allowance, when a cap can be resolved |

`allowance` contains `app_connection_id`, `cap_source`, `cap_rule_id`, `credit_mode`, `overrun_policy`, `currency`, `period`, `period_start`, `period_end`, `cap_amount`, `spent_this_period`, `remaining_base_allowance`, `available_credits`, `available_allowance`, and nullable `adjustment`

Use `allowance.available_allowance` for the reported amount available to spend. It includes base allowance and eligible credits. Null allowance is not proof of exhaustion. The profile can reflect the previous plan connection until the user sends a request with the new plan. See [Check available allowance](/startups/check-allowance)

The usage bucket field is `this_period`, not `this_month`. `usage.this_period.sell_cost` and `usage.total.sell_cost` contain reference-priced virtual spend despite the historical field name. Use the returned allowance object for spendable allowance rather than reconstructing it from usage

## Create a missing user during a read

Product-user GET requests return HTTP 404 when the user is missing. Add this header to create a missing user while reading:

```http
X-Zorveus-Upsert-Product-User: true
```

The header applies to `GET /product-users/by-external-id` and its `/credit-summary`, `/allowance-debt`, `/credit-grants`, and `/activity` subroutes. Omitting it or setting it to `false` keeps the request lookup-only. Only the literal strings `true` and `false` are accepted. Other values return HTTP 422

Opt-in creation requires an app owned by the service key's organization that has not been deleted. The new user is active with no existing credits, grants, usage, or debt. Existing profiles and statuses are preserved. The same read scopes apply with or without the header. Explicit `PUT` upsert, credit-grant writes, and inference attribution retain their existing creation behavior

<CodeGroup titles={["cURL", "Python", "TypeScript"]}>

```bash
curl --fail-with-body --get https://api.zorveus.com/product-users/by-external-id \
	-H "Authorization: Bearer $ZORVEUS_SERVICE_KEY" \
	-H 'X-Zorveus-Upsert-Product-User: true' \
	--data-urlencode "app_id=$ZORVEUS_APP_ID" \
	--data-urlencode 'external_user_id=customer_42'
```

```python
profile = service.product_users.get_by_external_id(
	app_id=app_id,
	external_user_id=authenticated_user_id,
	upsert_if_missing=True,
)
```

```typescript
const profile = await service.productUsers.getByExternalId({
	appId,
	externalUserId: authenticatedUserId,
	upsertIfMissing: true,
});
```

</CodeGroup>

Use `upsert_if_missing=True` on synchronous and asynchronous Python reads, or `upsertIfMissing: true` in TypeScript request parameters. The SDK sends the header automatically. An explicit boolean option takes precedence over raw upsert headers; existing raw-header calls remain supported when the option is omitted. Keep service keys on your backend and obtain the customer ID from trusted application state

## Upsert product user by external ID

<ApiEndpoint method="PUT" path="/product-users/by-external-id" auth="service_key" />

HTTP `200` returns `{ "product_user": { ... }, "created": true }` when the user is new. `created` is false for an update

| JSON field | Required | Meaning |
| --- | --- | --- |
| `app_id` | Yes | App owned by the service key's organization |
| `external_user_id` | Yes | Stable customer ID, non-empty |
| `display_name`, `email` | No | Profile enrichment |
| `metadata` | No | Custom profile object |
| `allowance_starts_at` | No | Timezone-aware subscription anchor |

```bash
curl --fail-with-body --request PUT https://api.zorveus.com/product-users/by-external-id \
	-H "Authorization: Bearer $ZORVEUS_SERVICE_KEY" \
	-H "Content-Type: application/json" \
	-d '{"app_id":"app_123","external_user_id":"customer_42","display_name":"Example user"}'
```

Omit `allowance_starts_at` to preserve it. Send null to restore calendar periods. A supplied timestamp cannot be in the future or older than the stored anchor. See [Allowance periods](/startups/allowance-periods)

## Get credit summary

<ApiEndpoint method="GET" path="/product-users/by-external-id/credit-summary" auth="service_key" />

Required query fields are `app_id` and `external_user_id`. Optional `currency` defaults to `USD`. HTTP `200` returns `currency`, `available_credits`, `active_grant_count`, `expiring_soon_amount`, `spent_this_month`, `spent_total`, `last_grant_at`, and `last_used_at`

The summary contains credits only. It excludes remaining base allowance. Monetary values are decimal strings

## Get allowance debt

<ApiEndpoint method="GET" path="/product-users/by-external-id/allowance-debt" auth="service_key" />

Required query fields are `app_id` and `external_user_id`. Optional `currency` defaults to `USD`. HTTP `200` returns `outstanding_amount`, `repaid_by_credits_total`, `repaid_by_base_total`, `currency`, and nullable `oldest_debt_at`

This is virtual allowance debt from `carry_overrun_forward`. It is separate from organization wallet debt. See [Overrun policies](/startups/configure-product-user-allowances#choose-the-overrun-policy)

## Grant credits

<ApiEndpoint method="POST" path="/product-users/by-external-id/credit-grants" auth="service_key" />

Creates the user if needed and adds a credit grant. With `external_reference`, a matching retry returns the existing grant. HTTP `201` returns `product_user`, `credit_grant`, and `credit_summary` for both creation and replay

| JSON field | Required | Meaning |
| --- | --- | --- |
| `app_id`, `external_user_id` | Yes | Identify the customer |
| `amount` | Yes | Positive decimal string, for example `"10.00"` |
| `external_reference` | No | Durable reference with 1 to 255 characters after trimming, or null for independent creation |
| `currency` | No | Defaults to `USD` |
| `source` | No | `admin_adjustment`, `service_key`, `purchase`, `promotion`, `monthly_allowance`, `support_credit`, or `import`. Default is `service_key` |
| `reason` | No | Human-readable reason |
| `expires_at` | No | Timezone-aware expiry timestamp, or null for no expiry |
| `display_name`, `email`, `metadata` | No | Optional details accepted with the grant |

```bash
curl --fail-with-body https://api.zorveus.com/product-users/by-external-id/credit-grants \
	-H "Authorization: Bearer $ZORVEUS_SERVICE_KEY" \
	-H "Content-Type: application/json" \
	-d '{"app_id":"app_123","external_user_id":"customer_42","amount":"10.00","currency":"USD","source":"service_key","external_reference":"purchase:purchase_123","reason":"Paid purchase purchase_123","metadata":{"purchase_id":"purchase_123"}}'
```

The grant includes `credit_grant_id`, `external_reference`, identifiers, `amount`, `remaining_amount`, `currency`, `source`, `reason`, `status`, `expires_at`, `metadata`, `created_at`, and `updated_at`. A returned grant can repay carried allowance debt, so do not assume its full amount becomes immediately spendable

On a backend with migration `20261027_0062`, reference uniqueness covers the organization and app, across users and grant sources. Matching normalized grant parameters recover the same grant. Changed parameters return HTTP 409 with `zorveus_product_user_credit_reference_conflict`. References survive key rotation and grant lifecycle changes. Neither `reason`, metadata, nor an idempotency header provides this guarantee. See [Idempotency and retries](/platform/idempotency) for the compared fields and normalization rules

## Find a credit grant by reference

<ApiEndpoint method="GET" path="/product-users/by-external-id/credit-grants/by-reference" auth="service_key" />

Required query fields are `app_id`, `external_user_id`, and `external_reference`. Requires `product_users:read` or a scope that includes it. HTTP 200 returns the grant directly with its current balance and status, including expired, exhausted, and revoked grants. HTTP 404 with `zorveus_product_user_credit_not_found` means no committed grant is visible in that scope

The lookup never creates a user, even with an upsert header. A 404 can race an unfinished creation. Repeat the original referenced POST if the outcome remains uncertain. Do not replace the reference with a new one

## List credit grants

<ApiEndpoint method="GET" path="/product-users/by-external-id/credit-grants" auth="service_key" />

Required query fields are `app_id` and `external_user_id`

| Optional query field | Meaning |
| --- | --- |
| `status` | `active`, `exhausted`, `expired`, or `revoked` |
| `source` | One of the grant sources above |
| `limit` | 1 to 1000, default 100 |

HTTP `200` returns `{ "credit_grants": [...] }`. There is no cursor or `has_more` field. Use the direct reference lookup for uncertain referenced grants. Do not treat a limited list as proof that a grant never existed

## List product-user activity

<ApiEndpoint method="GET" path="/product-users/by-external-id/activity" auth="service_key" />

Requires `product_users:read` or a scope that includes it. Required query fields are `app_id` and `external_user_id`. Optional fields are `type`, `from`, `to`, `currency`, `cursor`, and `limit`. The limit defaults to 20 and accepts 1 to 100. Timestamps require a timezone offset. `from` is inclusive and `to` is exclusive

HTTP 200 returns `product_end_user_id`, `items`, `next_cursor`, `has_more`, and `limit`. The discriminated item types include `usage`, `credit_added`, `credit_revoked`, `credit_expired`, `credit_refunded`, `credit_adjusted`, and `allowance_debt_repayment`. Usage items include saved `usage_metadata`, the signed product-user charge, base allowance and credit breakdowns, and per-grant allocations with saved metadata

A missing user returns HTTP 404 by default. Add `X-Zorveus-Upsert-Product-User: true` to create one in the service key's owned, non-deleted app. Existing profiles and statuses are preserved. Use the same filters with each returned cursor. Invalid or mismatched cursors return `zorveus_invalid_product_user_activity_cursor`. Empty or reversed time windows return `zorveus_invalid_product_user_activity_filter`, both HTTP 400

Read [Product-user activity](/startups/product-user-activity) for the full response, SDK calls, UI mapping, and historical-data limitations

## Errors

| HTTP status | Code or format | Meaning |
| --- | --- | --- |
| `400` | `zorveus_invalid_external_user_id` or other validation code | A supplied value is invalid |
| `401` | `zorveus_malformed_or_missing_service_key`, `zorveus_unknown_service_key` | Missing, malformed, or unknown credential |
| `403` | `zorveus_service_key_inactive` | Revoked, disabled, or expired key |
| `403` | `zorveus_service_key_scope_required` | Missing read or write permission |
| `404` | `zorveus_product_user_not_found` | No user for this app and external ID |
| `422` | Validation `detail` array | Missing required query or body fields, or invalid schema types |

Zorveus application errors use `{ "error": { "code": "...", "message": "..." } }`. See [Error handling](/platform/errors)

## Prorated allowance

Send `X-Zorveus-Allowance-Change-Policy: prorate_increase` on Business inference to prorate an upgrade. The body alternative is `metadata.product_user.allowance_change`, which takes precedence

First-use and same-connection requests do not create a proration event. A transition requires active daily or monthly caps on both connections with the same period and currency. Decreases, uncapped plans, lifetime caps, or active direct product-user caps reject the transition policy. User OAuth connections reject it

`cap.amount` is the configured cap. `allowance.cap_amount` is the effective current-cycle amount. `allowance.adjustment` includes `type: "prorate_increase"`, `configured_cap_amount`, and `effective_at` when an adjustment applies

An accepted adjustment survives a later inference failure. Further upgrades add their prorated increase to the current effective amount. At renewal, the full configured cap applies. See [Prorated plan changes](/startups/prorated-plan-changes) for a worked response
