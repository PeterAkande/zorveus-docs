Credit grants allocate spendable virtual credit to a product user in your application. They are distinct from organization wallet balances and spending caps.

For admission checks, read [total available allowance](/startups/check-allowance). For purchased credits, follow [Grant credits after a payment](/startups/billing-integration).

Create or resolve the user and grant credit in one service key request:

<ApiEndpoint method="POST" path="/product-users/by-external-id/credit-grants" auth="service_key" />

```bash
curl -X POST https://api.zorveus.com/product-users/by-external-id/credit-grants \
  -H "Authorization: Bearer zrv_svc_your_service_key" \
  -H "Content-Type: application/json" \
  -d '{
    "app_id": "app_123",
    "external_user_id": "customer_42",
    "external_reference": "welcome:customer_42",
    "amount": "10.00",
    "currency": "USD",
    "source": "promotion",
    "reason": "Welcome credit",
    "expires_at": "2026-12-31T23:59:59Z"
  }'
```

## Connection credit enforcement modes

The app connection defines a `credit_mode` that governs allowance enforcement:

| Mode | Request with product user | Request without product user | Behavior |
| :--- | :--- | :--- | :--- |
| `enforce_if_present` (default) | Enforces base cap plus credits | Bypasses cap checks, records virtual spend | Recommended for keys serving both user traffic and internal jobs. |
| `enforce` | Enforces base cap plus credits | Enforces key-level cap | Strict enforcement across all traffic. |
| `track_only` | Allocates cap and credits without blocking | Allocates cap without blocking | Never rejects for allowance. Records `uncovered_virtual_spend`. |
| `disabled` | Bypasses cap checks and credits | Bypasses cap checks | Records virtual spend for reporting without quota limits. |

User OAuth app connections always return `credit_mode: "enforce"`. The update endpoint rejects any other value for user OAuth connections.

---

## Allowance formula and deduction order

When a product user sends an inference request on a capped key, Zorveus consumes allowance in this order:

1. **Remaining base allowance**: Zorveus checks the inference key spending cap. If base allowance remains, usage is applied to the cap first.
2. **Active credit grants (earliest expiration first)**: If the request exceeds remaining base allowance, the excess is deducted from active unexpired credit grants.
3. **Uncovered virtual spend**: In non-blocking `track_only` mode or when overruns occur, spend beyond the cap and credits is recorded as uncovered virtual spend.

If an inference key has no cap rule, virtual allowance is unlimited across all credit modes. The request succeeds, virtual spend is recorded, and zero product-user credits are consumed. Credits extend an existing cap; they do not enforce a quota where no cap is configured.

When the configured policy blocks an unfunded request, the gateway rejects the request with HTTP `403 Forbidden` (`zorveus_product_user_allowance_insufficient`). Overrun behavior also depends on the connection's policy.

## Grant with a service client

Create the [service client](/startups/service-keys#create-the-client) with `product_users:write`. After verifying the purchase in your payment provider, grant the amount your product assigns to it

<CodeGroup titles={["TypeScript", "Python"]}>

```typescript
const result = await service.productUsers.grantCreditByExternalId({
	appId: "app_123", externalUserId: "customer_42",
	amount: "10.00", currency: "USD", source: "purchase",
	reason: "Paid purchase purchase_123",
	externalReference: "purchase:purchase_123",
	metadata: { purchase_id: "purchase_123" },
});
console.log(result.credit_grant.credit_grant_id);
console.log(result.product_user.getTotalAvailableToSpend());
```

```python
result = service.product_users.grant_credit_by_external_id(
	app_id="app_123", external_user_id="customer_42",
	amount="10.00", currency="USD", source="purchase",
	reason="Paid purchase purchase_123",
	external_reference="purchase:purchase_123",
	metadata={"purchase_id": "purchase_123"},
)
print(result.credit_grant.credit_grant_id)
print(result.product_user.get_total_available_to_spend())
```

</CodeGroup>

Store the returned grant ID against your purchase. `external_reference` makes retries safe for the same grant parameters. Metadata alone does not deduplicate. Changed parameters return HTTP 409 with `zorveus_product_user_credit_reference_conflict`

Recover a grant with `service.productUsers.getCreditGrantByExternalReference({ appId, externalUserId, externalReference })` or `service.product_users.get_credit_grant_by_external_reference(app_id=app_id, external_user_id=user_id, external_reference=reference)`. The lookup returns the grant directly, including its current balance and status. Python also supports the asynchronous method with `await`

The lookup requires `product_users:read` or a scope that includes it. A 404 can race an unfinished creation. Repeat the original POST with the same reference and parameters if the outcome remains uncertain. See [Billing integration](/startups/billing-integration) and [retry rules](/platform/idempotency) before enabling retries

To inspect existing grants, call `service.productUsers.listCreditGrantsByExternalId({ appId, externalUserId, limit: 100 })` or `service.product_users.list_credit_grants_by_external_id(app_id=app_id, external_user_id=user_id, limit=100)`. The result contains `credit_grants`. It has no cursor

## Read carried allowance debt

With `product_users:read`, retrieve debt created by `carry_overrun_forward`. This is customer allowance debt, separate from wallet funding

<CodeGroup titles={["TypeScript", "Python"]}>

```typescript
const debt = await service.productUsers.getAllowanceDebtByExternalId({
	appId: "app_123", externalUserId: "customer_42", currency: "USD",
});
console.log(debt.outstanding_amount, debt.repaid_by_credits_total);
```

```python
debt = service.product_users.get_allowance_debt_by_external_id(
	app_id="app_123", external_user_id="customer_42", currency="USD",
)
print(debt.outstanding_amount, debt.repaid_by_credits_total)
```

</CodeGroup>

Use decimal strings when displaying the values, or an exact decimal library for arithmetic. Credits can repay carried debt before adding spendable allowance


## Credit units and conversion rates

The app's `credit_units_per_usd` is the default for new USD grants. A grant can supply its own rate. Omit the override to save the app default on the new grant

```typescript
const receipt = await service.productUsers.grantCreditByExternalId({
	appId,
	externalUserId: authenticatedUserId,
	externalReference: `purchase:${verifiedPayment.id}`,
	amount: "2.000000000000",
	creditUnitsPerUsd: "1500",
	source: "purchase",
});
console.log(receipt.credit_grant.remaining_credit_units);
```

```python
receipt = service.product_users.grant_credit_by_external_id(
	app_id=app_id,
	external_user_id=authenticated_user_id,
	external_reference=f"purchase:{verified_payment.id}",
	amount="2.000000000000",
	credit_units_per_usd="1500",
	source="purchase",
)
print(receipt.credit_grant.remaining_credit_units)
```

The $2 grant above starts with 3,000 credit units. Its saved rate stays fixed when the app default changes. Referenced retries preserve the original rate. Changing an explicitly supplied rate under the same reference returns HTTP 409

Grant creation, lists, reference lookup, and revocation return `credit_units_per_usd` and `remaining_credit_units`. An older grant without a saved rate uses the current app default. If neither rate exists, a positive balance has null credit units. Zero remaining USD returns zero units

`credit_summary.remaining_credit_units` sums all usable grants at their respective rates, independently of the grant list limit. If any positive usable grant has no conversion, the total is null. USD fields such as `remaining_amount` and `available_credits` retain their existing meaning

`allowance.remaining_credit_units` includes the remaining base allowance at the current app rate plus grants permitted by the selected connection. It is the field to display for the customer's total remaining credit units. Credit units and rates are exact decimal strings. Keep their precision when displaying or processing them

Rates must be positive finite decimal values with at most 12 digits before and 12 digits after the decimal point. An explicit grant rate requires USD. Existing grants in other currencies remain supported without conversion
