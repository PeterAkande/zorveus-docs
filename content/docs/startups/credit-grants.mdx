---
title: Product-user credit grants
description: Allocate consumable credit to one product user and choose how the connection enforces it.
---

Credit grants are balances assigned to a product user. They are separate from organization wallet funds and spending caps.

Create or resolve the user and grant credit in one service-key request:

<ApiEndpoint method="POST" path="/product-users/by-external-id/credit-grants" auth="service_key" />

```bash
curl -X POST https://api.zorveus.com/product-users/by-external-id/credit-grants \
  -H "Authorization: Bearer zrv_svc_your_service_key" \
  -H "Content-Type: application/json" \
  -d '{
    "app_id": "app_123",
    "external_user_id": "customer_42",
    "amount": "10.00",
    "currency": "USD",
    "source": "promotion",
    "reason": "Welcome credit",
    "expires_at": "2026-12-31T23:59:59Z"
  }'
```

The inference key `credit_mode` determines enforcement:

- `disabled` ignores product-user credits.
- `track_only` records attribution without blocking on credit.
- `enforce_if_present` enforces credit when a product user is attributed.
- `enforce` requires product-user attribution and sufficient credit.

Active grants are consumed according to the backend’s grant ordering. Do not implement a client-side deduction hierarchy. Read the credit-summary endpoint for the authoritative available balance.


## Balance Deduction 

When a product user sends an inference request, Zorveus deducts usage costs using the following order:
1. Inference key Spending cap allowance. If the product user call is made using an inference key with a spending cap, Zorveus first checks if the all the metered request of the product user is within the remaining allowance.
2. **Active Credit Grants (Earliest Expiration First).** If the inference spending cap is exceeded, Zorveus burns active non-expired credit grants assigned to the product user, if any is present.

If no active credit grants are present, the request is rejected with an error response indicating insufficient funds.
