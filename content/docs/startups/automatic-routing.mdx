---
title: Key priority, rotation, and fallback
description: Use multiple provider keys with different priorities, automatic rotation around failures and cooldowns, and optional Zorveus wallet fallback.
---

You can attach multiple keys for the same provider in **Provider Credentials** in the [Zorveus dashboard](https://app.zorveus.com) and give each one a priority. Zorveus tries eligible keys in priority order, rotates to the next key when one hits rate limits or upstream failures, and can optionally fall back to your Zorveus wallet.

Zorveus only selects between eligible credentials for the exact model you asked for. It does not switch your request to a different model ID automatically.

---

## How priority ordering works

For a credential to be eligible, it must be active, match the requested model's provider and model policy, and be accessible to the API key (`auto_resolve` or explicitly granted).

Zorveus orders eligible keys in two tiers:

1. **Explicit grants first**: Credentials granted directly to the API key are tried before organization-wide `auto_resolve` credentials.
2. **Lower `routing_priority` first**: Within each tier, smaller numbers run first. For example, a key with priority `10` runs before priority `20`, which runs before priority `30`.

A common setup is placing your primary high-quota key at priority `10` and one or more backup keys at priority `20` and `30`. Do not rely on two keys with the same `routing_priority` receiving an even 50/50 split.

---

## Rotation and quota cooldown

When a primary key hits an eligible upstream error (such as a provider rate limit or quota exhaustion), Zorveus rotates to the next eligible backup key in priority order.

Keys that enter quota cooldown move behind healthy candidates until cooldown clears. Cooldown is temporary. It does not permanently disable the key, and Zorveus prefers it by priority again once it recovers.

---

## Optional wallet fallback

You control what happens if your BYOK keys fail with `auto_fallback_to_wallet` in **Provider Credentials**:

- **No matching BYOK key**: If no active BYOK credential matches the requested model, Zorveus uses its managed wallet-funded route (when available and funded). Turning off `auto_fallback_to_wallet` does not block managed routes when no BYOK credential matched in the first place.
- **Matching BYOK key fails**: Zorveus tries any backup BYOK keys first. If none succeed and `auto_fallback_to_wallet` is enabled, Zorveus can fall back to a managed wallet-funded route as long as one exists and your wallet has enough funds to reserve.

Wallet fallback changes who pays for that request:

- Requests served by your provider key record `billing_mode: "byok_external"` (plus any configured Zorveus platform fee).
- Requests served by wallet fallback record `billing_mode: "wallet"` and bill your Zorveus wallet directly.

Test both paths in **Usage** in the dashboard before enabling `auto_fallback_to_wallet` in production.
